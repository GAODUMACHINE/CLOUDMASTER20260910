# ADR-010：审核台值班界面与中断态语义（v1.4.0）

- 状态：评审通过（v1.4.0-review-console-ui）
- 日期：2026-09-17
- 关联：ADR-001（守卫顺序与中断）、ADR-003（L2 人工审核链路）、ADR-008（审核台账）
- 对应用例：TC-HITL-001 / TC-HITL-003 / TC-HITL-004

## 上下文
ADR-008 补齐了审核台**后端**（`ReviewLedger` + `/api/review/*`），但值班只能靠 curl/Postman，没有界面；
并且实测发现中断态（`interrupt_before=["human_review"]`）的语义有三处缺陷：

1. **回显用户原话**：L2 中断时 state 里只有那条 `HumanMessage`，`/api/chat` 取 `msgs[-1]` 会把
   用户自己的话当成「AI 回复」返回，前端于是把用户消息又显示一遍。
2. **挂起态可被绕过**：待审期间再发一条**非危机**消息，图会继续执行 `human_review(decision=pending)`
   一路走到 END，工单的中断态随即失效 → 审核员裁决只会得到 409，**工单永远无法闭环**。
   等价于用户发一条普通消息就能绕开人工审核。
3. **孤儿工单静默成功**：裁决一个会话已被删除（或中断态已失效）的工单时，
   `update_state` + `invoke(None)` 不经过 `human_review`，接口却返回 `ok=True`、台账已闭环，
   而 `audit_log`/`contact_log`/`next_followup` 全空——值班员会误以为已处理完毕。

## 决策
1. **挂起占位**：中断态下 `/api/chat` 返回 `REVIEW_HOLD_REPLY`（就地安全提示，**不含任何热线号码**），
   并新增响应字段 `held_for_review`；前端在 `held_for_review=true` 时整段立即呈现、不做逐字动画
   （危机场景不应有动画延迟）。
2. **挂起期不推进图**：若该 thread 已停在 `human_review`，`/api/chat` **不再 invoke 图**，
   改用 `graph.update_state` 把用户消息追加进 state（供审核台看到完整上下文），并返回既有工单。
   效果：不生成自动回复、不重复登记工单、中断态不失效（不可绕过），同时省掉该轮模型调用。
3. **裁决前校验中断态**：`POST /api/review/decision` 先读 `graph.get_state(cfg)`：
   - 会话不存在 → **409**「会话已不存在，请勿据此闭环」；
   - `next` 不含 `human_review` → **409**「中断态已失效，不能重复裁决」；
   - 恢复执行后仍无 `audit_log` → **500**，且**不闭环台账**。
   四种情况都不会静默成功。
4. **`/web/review/` 值班界面**：待审队列（编号 / 风险分级 / 判定依据 / 已等待时长）→
   案件详情（判定依据 + 上下文 + 用户回信）→ 结论写回（approve/block + 联络对象 + 审核人标识）→ 结果回显。
   - 令牌由值班人员输入，只存 `sessionStorage`（不进 URL、不进 localStorage、不落任何日志）；
   - 所有服务端内容一律以 `textContent` 渲染，**绝不使用 `innerHTML`**，避免上下文/回信里的用户输入
     造成 XSS 或 DOM 注入；
   - 页面不展示、不保存任何热线号码（与 `/api/resources` 的红线一致）。

## 后果
- 正向：值班可在浏览器内闭环（TC-HITL-003/004 前端可达）；挂起态不可被用户绕过；工单不会被静默闭环。
- 约束：挂起期间用户消息只留痕、不回答（自动回复本就应处于暂停状态），恢复完全由审核结论驱动。
- 待办：审核人仍是**自填标识**（无登录、无角色分级）；多人值班需补鉴权与权限模型。
- 待办：`decision=approve` 的「联络监护人/紧急联系人」仍是 `noop` 桩（ADR-003 红线：测试/试点不发真实联络），
  转真实联络须单独评审。
